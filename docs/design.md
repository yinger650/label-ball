# 设计要点

## 为什么要单独攒数据

单帧检测器（COCO sports ball、WASB、FootAndBall 等）在这批 8K ERP 全景上不够用：比赛球通常只有 8–30 px，飞行时还有动态模糊，静态单帧人眼都经常找不到。多间隔残差 + DoG 增强后，飞行中的球是一块孤立白斑。信息在时间维度上，模型也必须吃多帧。

## 只标一个球

GT 定义为「比赛中正在使用的那一个球」。场边备用球、球门后的球一律不标。纯几何跟踪曾经被一个完全静止的备用球锁死——时空平滑代价下它反而是最优解。

## 视野跟着球走

标完一帧跳下一帧时，视野中心用最近两个已标点**线性外推**（不是沿用上一帧位置）。step=3 时快球两帧间能跑约 390 px。

## 为什么权威在 SQLite，不在 AOSS

旧做法用对象存在性当状态：`packets/` 有 zip 就能领，`claims/` 有对象算占用，`results/` 有对象算交卷。服务端只做解码 + DoG，公网站还要 `sync_packets.py` 镜像 zip，浏览器用 `aoss_client.js` 自己 List / Put。

这套在「几百个包、个位数标注员」时能跑。AI 进来之后不够用：

- 审核、逐帧打回、按模型统计通过率都要能查询，对象在不在表达不出来
- AOSS 不再写 `claims/` 之后，按「没被 claim 的 zip」数池深会恒等于全部已产包，产包端会以为池子永远满着
- 公网出口常被拒 GetObject，把 zip 镜像到公网站是权宜之计，不是架构

现在权威只在 `server/db.py` 的 SQLite（WAL）。`gt` 表有行才叫入库。服务端进程不持有 AOSS / ACP 凭证，也不下载 clip / dog。客户端拿到 `packet_id` + `aoss_key`（新包是前缀 `packets/{id}/`，旧 zip 以 `.zip` 结尾）后自己 GetObject。产包端把 DoG / Scan / 缩略件算一次；审核只播缩略视频 + canvas 叠加。

包状态：`available` / `leased` / `submitted` / `accepted` / `need_human` / `archived`。

租约：AI 30 分钟（靠心跳续期），人工 36 小时，修补 12 小时。过期租约在下一次 lease / pool / stats 时顺手收回。

发包：AI 不领已有 `pending` AI 提交的包；`need_human` 只发给人工 / 修补；「不重复发给同一 worker」按有没有**提交过**判，不按领过就永久拉黑（否则 `release` 一次包就烂在池子里）。修补即使提交过也能再领——可能被二次打回。

## 冷启动必须人工种子

`scripts/smoke_vlm.py` 在真实包 `260122__002__1703_1713` 上打过四级 × 四家。**L0 montage（1024 宽、8×4，约 505 px/格）四家命中率都是 0%**。全景里那颗 8–30 px 的球，拼版级根本看不见。

因此工作流把 L0 整级停用。没有先验时本地 DoG blob（`propose`）召回也很低（球贴着球员脚下时 top-8 约 8%），480 px 的 `refine1` 命中率只有约 38%。

AI 主循环（`client/run.py`）没有 ≥2 个可见点就 `release`，不硬跑。种子来源按顺序：`--seed-gt` → 本机工作区 `labels.json` → lease 带回的 prior / gt → `GET /api/v2/gt/<packet_id>`。

人工站有「只标头两帧交给 AI」：写满 2 个可见点后只写本机 `labels.json` 并释放租约，**不 submit**（submit 会把整包标成 accepted，AI 领不走）。同机、同一 `--work` 的 `client.run` 下一轮捡起来从外推入口跑。

带 2 帧种子的整链，标定扫 `chain_tol_cells` 时中位误差约 **9.9 px**（1.2 格宽 + 4 px 这一档；再松会换目标，再紧会挡掉真修正）。

## 审核为什么播缩略视频，不再打 sprite

产包端把 DoG 算一次，编成 `dog.mp4` + `scan_*.jpg`，并 POST 长边 1280 的缩略件给公网站。AI / 人工提交只传 labels JSON（约 50 KB），不再打 1–3 MB 的 sprite zip。

线上审核是**粗审**：播 `/thumb/{pid}/clip.mp4`，`W` 切 `dog.mp4`，canvas 叠标注点与轨迹。Scan 面板把标注折线叠在 `scan_time.jpg` 上，一眼看折线是否压在白线上。像素级细审走线下客户端「转标注」拉全清。

`frame_idx` 仍是源视频帧号。`clip` 第 i 帧 = `frame_start + decim*i`（29.97 → decim=1，59.94 → decim=2）。播放器用 `requestVideoFrameCallback` 的 `mediaTime` 换算。

色条时间轴：绿正常、黄插值、红低置信、灰不可见。打回的帧写 `need_human`，人工用 `kind=repair` 只修那几帧，AI 答案当初值。待修复池可多选打回待标注（`POST /api/v2/requeue`）：状态改回 `available`，清空 `need_frames`，之后按整包重标。

看板包列表展示三个最新时间戳：`produced_at` / `labeled_at` / `reviewed_at`。

## 坐标

- 标注端只存全景像素 `(pano_x, pano_y)`
- ROI 可以跨 ERP 接缝：`pano_x = (roi[0] + local_x) % pano_w`
- 球场 `field_u/v` 只在导出时用 FootballDet360 的权威几何补齐（`scripts/export_gt.py` 复用 `collect_results.qc` 与 `pano_pixel_to_field`）

## 已验证的事实

| 结论 | 说明 |
|---|---|
| CRF 16 不损球的可辨识度 | clip 与 dog 都用 CRF 16；dog 再加 `deblock=-3,-3` + `tune stillimage`，top-8 blob 召回与 JPEG q95 持平 |
| 缩略件长边 1280 只够粗审 | 8 px 的球缩成约 2.5 px；DoG 缩略用 maxpool 才留得住白斑，ffmpeg scale 会吃掉 |
| 约 46/100 路视频球场跨接缝 | ROI 必须用最小覆盖圆弧，不能用 min/max 包围盒 |
| 增强 σ 不能调大 | 球员会被糊成大白块；快球主要靠拨帧 |
| 帧号必须可反推 | `ffmpeg -copyts -ss T` + `stream.start_time` |
| L0 montage 四家 0% | 冷启动不能靠拼版找球，必须人工种子 |
| `glm-4.6v-flash` 免费池 429 严重 | `primary` 用 `glm-4.5v`；flash 只当降级 |
| DeepSeek vision 在 L2/L3 可用 | 每图 384 token 上限，默认角色没编进 `primary` |
| 带 2 帧种子整链中位约 9.9 px | `chain_tol_cells: 1.2` 扫出来的档 |
| `refine3` 窗是 45 px 不是 27 px | 27 px 接到 refine2 后面有约 59% 的帧返回 null（球不在窗里） |
| 球场四角能安全地当出场区掩膜 | 四角按 x 环绕插值成 `y_b(x)`，299 个人工 GT 点里 `y − y_b` 最小 −36 px；留 60 px 空中余量时 0 误杀，而边界上方就是看台 / 灯光 / 场外车流 |
| 出场区要压暗、不能置黑 | 短 ROI（h≈660）里出场区占 19%，全黑会让模型把整块画面当异常；滤波图 ×0.12、原图 ×0.35 就够让顶部峰值从 255 掉到 30，场内像素分毫不动 |
| 本地核验能把错点和 GT 分开 | 五项证据相乘：人工 GT 上中位 1.00 / p10 0.75，故意偏 40–150 px 的错点上中位 0.22 / p90 0.40，可用门限区间 (0.40, 0.75) |
| 灰度时间投影分不出「当前帧是哪一段」 | v1 的 `streak` 级中位误差 40 px 的根因。三段时间放进 BGR 三通道后（R=当前帧、G=之后、B=之前）中位 14.7 px / p90 25.9 px |
| 扫描图只够当中心，不够当答案 | 球慢时前后两段的 DoG 亮斑重叠，「纯红」像素只占 GT 点的 1.7%，模型看到的是偏红的品红/橙。所以 `scan` 级 `accept: false` |
| 九宫格时间确认的窗是 240 px、每格隔 2 原始帧 | 160 px 窗只有 47% 的帧在 t−8 时球还在框里。240 px + 隔 2 帧：100% 的帧至少 5 格看得见球，9 格总位移中位 55 px（看得出在动） |
| v1 每帧都答 = 精度被尾巴单方面拖死 | 2026-09-14 同一批 3 包 54 帧：v1 放弃率 0、precision@20px **35.2%**、中位 52.5 px；逐包 0.22/0.72/0.11。失败模式是「丢了就再也找不回来」——`refine2` 在 80 px 窗里中位误差 94 px（球压根不在窗里），而 `null_rate` 是 0，模型永远给答案 |
| v2 同口径 precision 66.7%（不弃帧） | 同一批 54 帧、同一天同模型：中位 52.5 → 7.1 px、p90 151.9 → 58.9 px、2.54 次调用/帧。掩膜 + `rgb_required` + `scan` 换掉 `streak` 三项都不花额外调用 |
| 离线扫门限**不是**在线成绩的下界 | 直觉上「弃帧只会更保守」是错的。离线扫（v2 输出 54 帧）说 gate 0.6 → 85.2%/42.6%，同一门限在线跑（v2_online06）只有 **63.6%/25.9%**。差别在于在线弃帧会改变后面每一帧的先验，而离线扫只是把点抹掉 |
| 核验门必须配「跟丢重找」，否则是负收益 | 上面那 63.6% 的根因：弃帧之后 `has_prior` 一直是真，`predict_next` 照旧从更旧的点往外推（`predict1` 中位误差滚到 105–128 px），没有任何一级负责重新找球 |
| 「模型说找不到」不能当跟丢信号 | v1 的 `streak` 挂在 `not refine2.ok` 上，三个包全是 ran=0 —— `refine2` 的 `null_rate` 是 0，模型永远给答案，哪怕窗里根本没有球（那时它的中位误差 94 px，窗只有 80 px）。跟丢要看**先验准不准**（`prior_r` / 上一帧有没有被弃），不能看模型愿不愿意说 null |
| 跟丢要先锚回最后一个可信点，别急着退回冷启动 | 冷启动是整条链最弱的一环：`propose` 全局初选中位误差 446–919 px，`confirm9` 在那些位置上 100% 回「没有球」（它是对的）。球速约 20 px/目标帧，240 px 的扫描窗从最后一个可信点算覆盖 ±6 帧，比冷启动强得多。`lost_after: 2` / `cold_after: 6` |
| 双视图投票**不能**无条件开 | 想拿「两票对不上」当怀疑信号，实测反而把 precision 从 73.1% 打到 54.2%（v2_vote，同一批 54 帧）。两个都带 RGB 的视图一起看错时会互相背书，`_run_vlm` 对「对得上」给的 ×1.15 加成把平均置信顶到 0.93–0.95，错点因此翻过门限。相关性高的两票，它们的一致不是独立证据 |
| 模型的自报置信不是可用的怀疑信号 | 答对答错都是 0.85–0.95。所有「置信低于 X 就怀疑」的条件（`accept_conf`、`vote.when`）实际上几乎从不触发 |
| `confirm9` 的窗写 160 会把它焊死 | yaml 里曾是 160 px，实测那个尺寸只有 47% 的帧在 t−8 那格还看得见球 → 一律回「没有球」。改回标定值 240 px |
| `confirm9` 只能问「有没有球」，不能问「有没有在动的球」 | 提示词原来把「逐格平移」写成硬条件，于是模型看见了球却因为「球停在球员脚下没动」而回 false（`scripts/probe_confirm9.py` 探出来的）。改成「在动的和停着的都算」之后，GT 位置召回 25% → 50%，偏 200 px 的负样本误报保持 **0%** |
| 整链 precision 的同配置重复方差约 ±3 点 | `v2_anchor06` 与 `v2_final` 是同一份配置跑两遍：73.1%/35.2% 与 70.8%/31.5%。54 帧 / 约 24 个答出点，二项标准误就有 9 个点。**在这个规模上别追小数点** |
| 到不了整体 85% 的瓶颈是「模型看不见球」，不是门限 | v2_final 逐包 precision 100% / 57% / 33%，而 v1 在后两包上是 22% / 11% —— 那两包两代工作流都跟不住，`refine2` 的 80 px 窗里中位误差 45–108 px。门限扫描在它们身上顶到 0.8 也只有 70.6% |
| 包级闸门才是「交出去的数据」的精度闸门 | 答出比例低 = 本地核验一直不同意 = 剩下那些点通常也不对。`MIN_FOUND_RATIO` 卡 0.35 时提交数据 precision 15/18 = 83%，卡 **0.45** 只提交第一包 → 100%，代价是另两包退回人工标两帧 |
